# 인플루언서 제안 심사

인플루언서 캠페인 확대 요청과 연간 전속계약 갱신을, 상신 전에 점검하는 도구임.
점검까지만 하고 상신과 결정은 사람이 함.

**[앱 열어 보기](https://jieeeui.github.io/ax_samil/)** · 브라우저 안에서 실행됨. 설치 필요 없음.

## 왜 만들었나
- 인플루언서 활동과 SNS 반응이 캠페인(이벤트) 성과에 바로 영향을 준다는 점이 흥미롭고 어떤 이슈를 반영할 수 있을지 해 보고 싶어서 이 업무를 골랐음
- 성과를 매출(GMV)로만 보고하면 이상하다고 생각했음. 음식점에서 낸 매출가에서 재료비와 인건비를 빼야 순이익이 남음. 쿠폰·반품·광고비를 빼고 "남는 돈"으로 다시 계산함
- 재계약이 확인 없이 자동으로 이어지는 점이 가장 이상했음. 그것도 손실을 내는 인플루언서와 재계약이라 더 이상하게 생각하여 자동화에 해당 이슈도 넣으려고 했음
- 신입 사원과 실무자가 거부감 없이 쉽게 쓰고, 점검에 드는 시간이 줄어야 자동화라고 생각했음
- 처음에는 업무 전체를 자동화하려 했으나, 멘토 피드백을 받고 실수가 가장 잦은 "상신 전 점검" 한 구간으로 줄였음

## 무엇을 하나
- 캠페인별 실질 성과 계산 (광고비를 뺀 뒤에도 남는지)
- 누가 승인해야 하는지 판정
- 실제 결정 기한과 남은 일수 표시, 기한이 다가오면 경고
- 빠진 정보와 물어볼 곳 정리

하지 않는 것: 사람 대신 상신·승인하는 일, 실제 결재 시스템 연동, 실제 통보·발송, 로그인. 화면의 상신·승인 버튼은 사람이 누르는 시연용(모의) 입력임.

## 자동화 조건
| 상황 | 결정하는 사람 |
|---|---|
| 현금이 최소 기준 30억 원 아래로 떨어질 것으로 예상되는 기간에 돈이 나가는 건 (금액 무관) | CEO/이사회 |
| 전속계약 연 10억 원 초과 | CEO/이사회 |
| 캠페인 건별 1천만 원 초과, 또는 기안 총액 1억 원 초과 | Masil 대표 + 그룹 보고 |
| 위에 해당 없음 | 마케팅 전결 |

- 혜인 전속계약(연 고정 피 28억 원)은 7월 17일까지 통보하지 않으면 같은 조건으로 1년 자동 갱신됨
- 갱신 후 해지하면 남은 고정 피의 50%가 위약금임. 자동 갱신도 체결로 봄
- 결정 기한 = 확정기한과 집행 예정일 중 빠른 날. 집행이 확정기한보다 먼저인 기안이 12건 있음
- 결정 없이 기한이 가까워지면 "조건 변경 통보 · 해지 통보 · 상신 후 승인" 중 하나를 고르라고 경고함

## 결과 (가정을 정해 계산한 값)
- 기안 25건 중 광고비를 빼면 손실인 캠페인 6건, 요청액의 약 42.8%
- 현금 부족 예상 구간 7월 21일 ~ 8월 21일, 이 구간에 집행되는 12건은 CEO/이사회 대상
- 오배송·불량 반품이 전체의 약 51%(1,719건 중 878건)라, 인플루언서 책임으로 돌리지 않는 보기를 따로 둠

## 직접 눌러 보기
처음 상태에서 위에서부터 순서대로 누르면 됨. 맨 위 줄이 혜인 연간 계약임.
1. 링크를 열고 "보는 사람"을 Masil 재무팀으로 바꿈 (바꾸기 버튼)
2. 혜인 연간 계약을 열어 "재무 확인 완료"를 누름
3. 확인 칸을 체크하고 "CEO/이사회에게 올리기"를 누름 (상신은 되돌릴 수 없음)
4. "보는 사람"을 CEO/이사회로 바꾸면 승인·거절·보류를 고를 수 있음. "정보가 더 필요하면 보류하기"를 열어 확인할 내용·담당·기한을 넣고 보내면 확인 요청이 생김
5. 아래 "확인 요청" 탭에서 "불리한 답변: 8월 10일에 지급" 같은 답을 누르면 다시 계산됨 (정보 부족 흐름)
6. 설정에서 "LC-0001 45일 가정"으로 바꾸면 현금 부족 구간이 사라지고 승인 경로가 다시 계산됨 (조건 변경)
7. 설정에서 오늘 날짜를 7월 14일로 옮기면 7월 17일 기한 경고가 뜸
8. 처음으로 돌리려면 설정의 "전체 초기화"를 누름

## 내 컴퓨터에서 실행
```bash
npm ci
npm run dev        # http://localhost:3000
```
- 대회 원본 파일(주문·반품·광고비·자금 표)이 필요함. 저장소에는 올리지 않았으므로 `DATA_DIR`로 위치를 지정함
- 선택: `DATABASE_URL`(PostgreSQL), `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`(AI 문장). 키가 없으면 자동 작성 문장을 씀
- 위 링크의 실행판은 `demo/`에서 만듦. `npm run demo:snapshot`(원본 필요)과 `npm run demo:build`

## 숫자의 근거
모든 값에 "원본에 있음 / 외부 기준 / 직접 정한 가정" 표시를 붙였음. 직접 정한 가정에는 주문당 판매 수량, 환불 시 원가 회수 여부, 연체 대금 처리 방식 등이 있음. 가정을 바꿔도 손실 캠페인 6건은 그대로임.

## 한계
- 일부러 범위를 좁혔음. 상신 전 점검 한 구간만 맡고, 실제 결재 시스템 연동, 부서 간 조율, 예외 상황의 판단은 사람이 함. 결재 이후 기능(재무 반려, 통보 작업 등)은 시연용으로만 구현했고 기본 화면에서는 숨겨 둠(설정에서 켬)
- 로그인과 접근 통제가 없음. 역할 전환은 시연용임
- 승인·회신·알림은 실제로 보내지 않고 모의로 처리함
- 일부 승인 단계는 원본에 없는 교육용 가정임
- 점검 한 구간으로 좁혔지만, 기존 업무 방식을 유지하는 데까지는 가지 못했음. 점검 결과를 기존 결재 문서로 가져가거나 새 기안을 넣는 방법이 없어, 재무 확인·상신·결정을 이 화면 안에서 눌러야 함. 다음에는 상태 관리보다 이 두 가지를 먼저 만들 것임
- 링크의 실행판에는 원본 파일을 올리지 않고, 화면에 필요한 일부 표(캠페인·인플루언서 목록, 기안 25건, 외부 기준값)와 계산 결과만 담았음. AI 문장 다듬기는 쓰지 않으며, 상태가 각자 브라우저에만 저장됨
- 운영용 PostgreSQL의 트랜잭션 경로는 실제 DB로 시험하지 못했음. 시험은 내장 DB(PGlite)로 함
- AI 문장 다듬기는 Gemini 키로 일부만 확인했음
- 실제 사용자에게 써 보게 하는 시험과 시간이 얼마나 줄어드는지의 측정은 하지 못했음

## 만드는 과정의 한계
- 방향을 바꾼 뒤에도 AI가 이전 계획을 기준으로 진행한 적이 있었음. 멘토 피드백으로 업무 전체 자동화에서 "상신 전 점검" 한 구간으로 줄인 뒤에도 그랬고, 사람이 짚어서 바로잡았음. 방향이 바뀌면 AI의 계획이 새 방향과 맞는지 사람이 계속 확인해야 함
- AI가 만든 결과도 그대로 믿지 않고 검증함. 다른 AI(Codex)에게 코드 리뷰를 받아 AI 요약이 숫자의 의미를 잘못 검사하는 문제 등 5건을 찾아 고쳤음 (`docs/reviews/`)

대회 과제로 만든 기록이며, 가상 기업과 허구 데이터를 씀.
