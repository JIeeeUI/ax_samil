## 재현된 문제 (우선순위순)
### R1 [높음] AI 숫자 검증이 수치의 의미나 문장의 사실 여부를 검사하지 못한다
- 위치: src/ai/verify.ts:33, src/ai/assist.ts:32, 66.
- 실제 혜인 명목 ROAS 1.36 / 실질 ROAS -0.20.
- 가짜 응답: “과거 실질 ROAS는 1.36입니다. 지급 일정은 모두 확인됐으며 추가 확인은 필요 없습니다.”
- 결과: source=ai, note 빈 문자열로 통과했다. 명목 수치를 실질 수치에 대입했고 지급일도 미확인인데 확정 문장으로 바뀌었다.
- 영향: 적자를 흑자로 오해시키는 결재자용 요약이 표시될 수 있다. 실제 Gemini가 이 문장을 생성했다는 뜻은 아니며, 생성했을 때 검증기가 막지 못함을 입증했다.
- 권장: 수치/경로/누락 정보는 서버 템플릿으로 고정하고 AI는 표현만 보조하거나, 필드별 구조화 응답을 받아 원본과 대조 후 서버가 문장을 구성한다. 단순 숫자 허용 목록으로 사실 검증을 표방하지 않는다.

### R2 [높음] 처리 중 저장 오류가 나면 상태만 바뀌고 기록이 남지 않는다
- 위치: src/app/service.ts:493–496; src/store/db.ts, src/app/commands.ts:10.
- 재현: 메모리 DB에서 addEvent가 실패하도록 주입하고 PLAN-001 재무 확인 실행.
- 결과: 오류를 반환했지만 상태는 routed로 바뀌었다. 이력은 received/calculated뿐이며 confirm_finance가 없다.
- 영향: 사용자는 실패했다고 보고 재시도하지만 이미 처리된 상태가 되어 재시도도 막힐 수 있다. 누가 확인했는지 증거가 누락된다.
- 권장: 상태 전이·관련 요청·이력 저장을 같은 DB 트랜잭션으로 묶는다. 단순 예외 잡기는 롤백이 아니다.

### R3 [중간] 존재하지 않는 보류 기한을 저장할 수 있다
- 위치: src/workflow/status.ts:60–67; src/store/schema.ts의 text 날짜 열.
- 재현: 제출된 계약을 dueDate=2026-99-99로 보류.
- 결과: 요청 기한 2026-99-99가 그대로 저장됐다.
- 영향: 기한 비교와 안내가 비정상으로 작동할 수 있다. 일반 브라우저 날짜 입력은 막아도 서버 호출에는 검증이 필요하다.
- 권장: 기존 isIsoDate로 달력 날짜를 검증하고, 업무상 허용되는 보류 상한도 통일한다.

### R4 [중간] 기한이 임박하면 의견을 붙이라는 안내와 서버의 필수 조건이 다르다
- 위치: src/app/service.ts:500–507; app/(shell)/cases/[id]/page.tsx:64.

- 원인: 서버는 반려 이력이 있을 때만 의견을 필수로 검사한다. UI는 확장 기능 설정에도 영향을 받는다.

### R5 [중간] 날짜가 필요한 확인 요청도 빈 회신으로 완료 처리할 수 있다

## 신입·기존 사원 사용성
### 잘된 점
- 누가 다음에 처리하는지 제목에 표시하고 현재 단계 막대를 보여 준다.
- 검색, 짧은 상태, 최상위 주의 태그와 추가 개수, 중요도 정렬이 있다. 검색 결과 개수는 aria-live로 전달한다.
- 근거는 접어서 필요할 때 펼칠 수 있고, 타임라인 시작 7/21·종료 8/21이 표시된다.
- 시연용 오늘과 역할 전환이 표시되고 원본 표본/회사 규모 금액을 합산하지 않는 안내가 있다.
### 개선할 점
- 신입에게 “내 차례 0건”은 막힌 것처럼 보일 수 있다. “재무 확인을 기다리는 26건입니다. 완료되면 내 차례에 표시됩니다”처럼 이유와 다음 담당을 설명하면 좋다.
- 상신·기안·실효 기한·명목/실질 ROAS·LC-0001 같은 용어는 여전히 남아 있다. 현재의 쉬운 표현을 유지하며 짧은 풀이/계산 예시를 제공한다. 실제 신규 사용자 테스트는 아직 수행하지 않았으므로 직관적이라고 확정할 수 없다.
- 상세 화면에서 승인 경로·기한·현금 차이가 여러 곳에 반복된다. 상단은 결론과 다음 행동, 접힌 영역은 상세 증거로 나누면 읽는 부담이 줄어든다.
- AI 로딩은 “최대 30초”라고 하지만 모델별로 30초 제한을 새로 적용하며, 재시도 가능한 HTTP 오류 후 다른 모델을 호출한다. 전체 대기 시간이 30초를 넘을 수 있으므로 전체 시간 제한 또는 실제 진행 안내가 필요하다. 실제 90초 호출을 실행한 것은 아니다.

## 시연과 실제 업무 사용의 구분
- 로그인 대신 사용자가 직접 고른 역할 쿠키를 신뢰한다(app/session.ts). 시연 의도와 맞지만 실제 직원을 구분하거나 결재 권한을 증명하지 못한다.
- 시계·가정·초기화는 공유 DB에 반영된다. 설정 페이지는 전체 초기화를 제공하며 서버 actReset에도 관리자 권한 검사가 없다. 여럿이 쓰는 실제 서비스로 전환하려면 접근 권한과 사용자/조직별 데이터 범위를 먼저 정해야 한다. 배포 DB를 초기화하여 검증하지 않았다.
- scripts/demo.ts는 DATABASE_URL이 있으면 경고만 출력하고 해당 DB를 초기화한다. 공유/운영 DB 실수 방지용 실행 차단 또는 별도 확인이 권장된다. 이번 리뷰에서는 해당 환경 변수가 없는 것을 확인했다.
- 이번 범위에서는 시연용 역할 전환을 임의로 제거하거나 결재 흐름을 변경하지 않았다.
